## 第一轮：订阅录入规范化
### 发现
订阅持久化格式为名称 + TAB + URL。原有新增/编辑路径仅做首尾 trim，没有在写入前清除字段内部控制字符。名称或 URL 若含 TAB 会破坏分隔格式；换行等控制字符也可能造成地址不可预期。

### 修复
- 新增 `normalizedSubscribe(name, url)` 纯逻辑规范化函数。
- 名称和 URL 统一过滤 ISO 控制字符并 trim。
- 名称为空时回退 URL；URL 清理后为空时拒绝录入。
- 点播、直播新增/编辑和本地配置导入共用此入口。
- 新增测试覆盖控制字符、空名称回退和空 URL 拒绝。

## 第二轮：点播订阅切换失败状态审查
### 发现
- `AppBootstrap.switchVodSubscription(url)` 先调用 `ConfigRepository.switchVodSource(url)`，后者立即写入 `API_URL`、更新订阅历史，并可能清理点播/直播多仓线路状态。
- 随后 `onApiUrlChanged()` 会先使当前内存点播配置失效，再异步加载新源。
- 新源加载失败时，`startInit()` 只将启动状态设为 `Boot.Error` 并结束本轮，没有恢复切换前的 URL、线路选择或旧配置。
- `ConfigManageViewModel.switchToVod()` 在启动异步加载后立即把 `activeUrl` 更新为新 URL；失败路径没有对应回滚。因此持久化选中源、界面快照与可用配置之间可能不一致。
- `ConfigLoader` 的失败回退只尝试当前新 URL 对应的缓存，不会自动回到切换前的源。

### 处理结论
这是跨 `ConfigRepository`、`AppBootstrap`、`ApiConfig`、历史线路及配置缓存的事务问题。不能只把 `API_URL` 改回旧值：切换过程中可能已经清理多仓线路、重置内存配置并改变 live-follow 关系。当前轮先记录并界定完整回滚边界，不做可能丢失线路状态的局部补丁。

### 下一步
设计可测试的切换快照/事务：至少覆盖点播 URL、直播跟随关系、点播与直播多仓线路选择、活动配置加载状态及代际；成功后提交快照，失败后恢复快照并重新加载旧配置。另需覆盖连续快速切换时旧请求不得回滚新请求。
